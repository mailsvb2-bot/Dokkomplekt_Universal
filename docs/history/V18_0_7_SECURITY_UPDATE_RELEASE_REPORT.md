# Dokkomplekt Universal 18.0.7 — отчёт по security/update hardening

> Исторический отчёт версии 18.0.7. Он не описывает текущее дерево 18.0.8 и не должен использоваться как актуальное доказательство; см. `RELEASE_VERIFICATION_V18_0_8.md`.


Дата подготовки: 16 июля 2026 года.

Релиз 18.0.7 закрывает 64 класса дефектов в лицензировании, профессиональных popup, проверке обновлений и release-контурах. Список ниже описывает именно закреплённые кодом и регрессионными контрактами классы, а не число изменённых строк.

## Лицензирование и активации — 1–16

1. Повторная активация того же компьютера больше не создаёт новую activation-запись.
2. Повторная активация того же компьютера больше не расходует дополнительный слот тарифа.
3. Идемпотентный ответ возвращает исходный activation ID, а не новый случайный идентификатор.
4. HTTP-ответ явно различает новую активацию и `already_activated`.
5. Выдача лицензии запрещена, пока заказ не подтверждён как оплаченный.
6. Выдача лицензии запрещена для компьютера, который не прошёл подтверждённую активацию.
7. Лицензия включает весь подтверждённый набор компьютеров заказа, а не только компьютер последнего запроса.
8. Повторная выдача для неизменившегося набора компьютеров возвращает действующий документ лицензии.
9. Изменение подтверждённого набора компьютеров приводит к новому документу лицензии.
10. Отсутствующий server-side issue-token secret больше не переводит endpoint в fail-open.
11. Пустой issue-token secret считается отсутствующим и блокирует выдачу.
12. Переданный токен сравнивается с серверным секретом в constant-time режиме.
13. Issue-token берётся только из серверной конфигурации и не становится trust anchor клиента.
14. In-memory и PostgreSQL storage используют один контракт идемпотентной активации и выдачи.
15. PostgreSQL сериализует конкурирующую выдачу блокировкой строки заказа в транзакции.
16. Повреждённый license JSON не может совпасть с другим документом как два «пустых» набора машин.

## Профессиональные popup — 17–30

17. Ответ на неизвестный field ID блокирует применение popup.
18. Повторяющийся ответ на один field ID блокирует применение popup.
19. Ошибки ответа возвращаются отдельным списком и не маскируются только флагом `accepted`.
20. Значение типа number отклоняет `NaN`.
21. Значение типа number отклоняет положительную и отрицательную бесконечность.
22. Денежное поле отклоняет `NaN` и `Infinity` до нормализации.
23. Денежное поле отклоняет строки с посторонним текстом вместо бесконтрольного удаления символов.
24. Денежное поле отклоняет несколько знаков и несколько десятичных разделителей.
25. Денежное поле ограничивает дробную часть двумя знаками.
26. Конструктор popup запрещает повторяющиеся field ID.
27. Конструктор popup запрещает некорректные semantic field ID.
28. Конструктор popup запрещает пустые заголовки и повторяющиеся варианты ответа.
29. Связанное поле не может ссылаться само на себя или на отсутствующее поле.
30. Граф связанных полей проверяется на циклы до сохранения конфигурации.

## Подписанные обновления — 31–50

31. Для обновлений используется отдельный Ed25519 trust anchor, не совпадающий по назначению с ключом лицензий.
32. Manifest URL встраивается при сборке и не принимается аргументом из интерфейса.
33. Update public key встраивается при сборке и не принимается аргументом из интерфейса.
34. Неподписанный или неверно подписанный manifest отклоняется.
35. Поддерживается только явно заявленная схема `dokkomplekt.update.v1`.
36. Сравнение версий выполняется полноценным SemVer-парсером, включая prerelease.
37. Пакет выбирается только для текущей ОС и архитектуры.
38. Manifest и пакет разрешено получать только по HTTPS.
39. URL с credentials отклоняется.
40. URL с fragment отклоняется.
41. Redirect запрещён на уровне HTTP-клиента.
42. `localhost` и поддомены `.localhost` отклоняются.
43. Private, loopback, link-local, unspecified, multicast и служебные IP отклоняются после DNS-разрешения.
44. Размер manifest ограничен 64 KiB.
45. Размер пакета ограничен 512 MiB и подписан в manifest.
46. `Content-Length`, фактически прочитанный размер и подписанный размер сверяются.
47. SHA-256 вычисляется потоково и сверяется до публикации файла.
48. Временный файл создаётся с `create_new`, а при любой ошибке удаляется.
49. Имя артефакта ограничено безопасным ASCII-набором и защищено от path traversal.
50. Windows reserved names `CON`, `PRN`, `AUX`, `NUL`, `COM1..9`, `LPT1..9` запрещены.

## CI, supply chain и выпуск — 51–64

51. В интерфейс добавлена видимая кнопка «Проверить обновления».
52. Frontend вызывает update-команду без возможности подменить URL или ключ.
53. Tauri registry и TypeScript command surface проверяются на точное совпадение.
54. Update-команда закреплена DTO-контрактом и UI-регрессиями.
55. Добавлен детерминированный генератор подписанного update manifest.
56. Приватный update seed читается только из environment и не хранится в репозитории.
57. GitHub Actions используют минимальные `contents: read` permissions.
58. Concurrency отменяет устаревшие quality-прогоны и не дублирует installer release.
59. Для jobs установлены явные timeout.
60. Python structural gate отделён от настоящего Rust compile gate и не выдаёт source scan за Cargo-проверку.
61. Релиз остаётся fail-closed без `Cargo.lock` и маркера полного Rust gate.
62. На installer runner повторно выполняются fmt, check, Clippy `-D warnings` и Rust tests.
63. Добавлены `SECURITY.md`, `CONTRIBUTING.md`, `.env.example` и фиксированный список dev-зависимостей Python.
64. Исходный архив строится детерминированно, снабжается полным SHA-256 manifest и проверяется после упаковки.

## Граница подтверждения

В текущей Linux-среде нет `cargo`, `rustc`, `rustfmt` и `clippy`. Поэтому этот отчёт **не объявляет**, что изменённый Rust-код прошёл компиляцию, Clippy или Rust-тесты локально. Workflow настроен fail-closed: installer/release не может считаться подтверждённым до прохождения реального Rust gate и Windows-проверок Word COM/NSIS.
