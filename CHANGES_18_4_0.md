## Исправленные дефекты

### E5 — сопоставление классов риска по подстроке без границ слов

`field_risk` сравнивал подстроки. Следствия на реальных именах полей:

| поле | было | стало |
|---|---|---|
| `hr.winner_bonus` | Critical (подстрока `inn`) | High (префикс `hr`) |
| `org.beginning_date` | Critical (подстрока `inn`) | High (слово `date`) |
| `spinner.state` | Critical (подстрока `inn`) | Low |
| `education.candidate_id` | High (подстрока `date`) | Low |
| `task.update_flag` | High (подстрока `date`) | Low |
| `doc.validated_by` | High (подстрока `date`) | Low |

Специалист, назвавший поле `winner` или `update`, получал нерушимую
блокировку без объяснения.

Теперь сопоставление идёт по сегментам (`split('.')`) и словам
(`split('_')`), целыми токенами. **Проверено: 40/40 на наборе реальных
и провокационных имён.**

### E4 — дрейф между рантаймом и калибровкой

`automation_quality.rs::field_risk` (Rust) и `measure_domain.py::_is_high_risk`
(Python) были двумя независимыми реализациями и расходились. Из восьми
проверенных полей **шесть** рантайм гейтил, а калибровка не измеряла вовсе:

`subject.address`, `medical.diagnosis_code`, `amount.vat`, `employee.salary`,
`legal.claim_subject`, `org.bank_account`.

То есть подписанный артефакт калибровки авторизовал автопечать для полей,
ошибки на которых он никогда не наблюдал.

Обе стороны теперь читают `resources/field_risk_registry.json`. Старая
Python-функция сохранена как `_legacy_is_high_risk` исключительно ради
регрессионного теста, доказывающего факт расхождения.

### E3 — мёртвая ветка автозапуска

```
cluster = domain_conf*0.45 + role_conf*0.35 + top*0.20     порог: >= 0.60
```

Когда домен выводился по сходству с настроенными шаблонами,
`domain_confidence` оставалась нулём. Максимум тогда:

```
0*0.45 + 0.99*0.35 + 1.0*0.20 = 0.5465  <  0.60
```

Ветка была недостижима **ни при каких данных**. Любой документ, чей домен
опознан только по сходству, гарантированно уходил на ручное подтверждение.

Теперь fallback возвращает домен вместе с уверенностью
`(similarity * 2.4).clamp(0.0, 0.80)`. При минимальном пороге входа
`similarity >= 0.12` это даёт `domain_conf = 0.288`, и автозапуск
становится достижим — но не автоматичен: одного сходства по-прежнему мало,
нужны роль и совпадение шаблона.

**Проверено арифметикой по константам, прочитанным из исходника.**

### E6 — подстрочное сравнение ролей

`role_equivalent` использовала `actual.contains(expected)`, из-за чего
`role_equivalent("contract", "employment_contract") == true`: договор
поставки подтягивал кадровый шаблон трудового договора.

Сравнение переведено на полные сегменты идентификатора. Дополнительно
разведены роли, сопоставляемые со свободным русским именем шаблона:
гражданско-правовой договор теперь явно исключает «трудовой».

### E1 (частично) — контрольная сумма заменяет числовой порог

Пороги `High 0.98` и `Critical 0.995` превышали потолок всех автоматических
источников: `0.97` у детерминированного парсера, `0.99` после `.min(0.99)`
в `semantic_engine.rs:465` и `semantic_llm.rs:194`. Сравнивалась вписанная
человеком константа с вероятностным порогом — величины разной природы.

Теперь значение, прошедшее **настоящую** математическую контрольную сумму,
не блокируется числовым порогом. Контрольная сумма — факт, а не оценка.

Список классов намеренно короткий, и каждое исключение обосновано:

| валидатор | включён | почему |
|---|:--:|---|
| `validate_inn` | да | 1 к.ц. (10 знаков) / 2 к.ц. (12 знаков) |
| `validate_snils` | да | mod 101 |
| `validate_ogrn` | да | mod 11 |
| `validate_kpp` | **нет** | проверка ФОРМАТА: любые 9 символов нужного вида |
| `validate_cadastral` | **нет** | проверка ФОРМАТА: четыре группы цифр |
| `validate_vin` | **нет** | к.ц. считается **только** для VIN на 1..=5; для европейских и японских — `Ok` после формата |
| `validate_bank_account_with_bik` | нет | настоящая к.с., но требует двух полей; шлюз видит одно |

**Проверка происхождения остаётся выше по коду и не отменяется.**
Контрольная сумма доказывает «это валидный ИНН», но не «это нужный ИНН»:
подмена ИНН поставщика на ИНН покупателя проходит её идеально.

### E12 — молчаливый ноль при неоднозначности

Если ни один шаблон не брал порог рекомендации `top >= 0.56`, маршрутизатор
возвращал пустой список, а `bundle_decision.rs` проваливался в
`NoSafeProposal` с сообщением «Не удалось безопасно определить комплект.
Выберите документы один раз для этого типа дела» — **выбрасывая уже
посчитанные ранжированные кандидаты**, которые лежали в `routing.matches`.

Типичный случай: два близких шаблона делят оценку («акт выполненных работ»
против «акта приёма-передачи»), ни один не дотягивает, и специалист получает
пустой экран вместо выбора из двух.

Теперь при `0.32 <= top < 0.56` выдаётся `AmbiguousCandidates`: кандидаты
именуются в вопросе, специалист выбирает одним нажатием, выбор уходит
в корпус обучения. Изменение помещается целиком в `bundle_decision.rs` —
рантайм уже печатает `question` и `document_ids` на review-ветке.

Безопасность не ослаблена: `auto_apply = false`, `review_required = true`,
а review-ветка рантайма делает ранний возврат **до** формирования плана
генерации, поэтому названные кандидаты не могут стать планом.

Порог `CANDIDATE_FLOOR = 0.32` взят тот же, что уже используется для
документов-спутников, и на это есть тест против дрейфа: две независимые
константы «достаточно похоже» разъехались бы со временем.

Попутно исправлено ложное сообщение маршрутизатора «В текущем наборе нет
достаточно похожего документа», которое выдавалось и тогда, когда похожие
были, но не взяли порог.

### Двойной учёт доказательств в классификаторе домена

Найдено сквозным тестом после того, как появился компилятор.

`classify_source_domain` добавляла +4 за КАЖДОЕ поле с доменным префиксом,
независимо. Измерено:

| поля дела | уверенность домена |
|---|---:|
| `contract.number` | 0.667 |
| `+ contract.date` | 0.800 |
| `+ contract.subject` | 0.857 |
| `+ legal.claim_subject` | 0.889 |

Все они извлекаются из одной фразы «№ 77 от 03.03.2026». Одно доказательство,
учтённое столько раз, сколько полей оно породило.

Хуже: производный сигнал перевешивал прямой. Фраза «настоящий договор»
(вес 3, сильнейшая одиночная для Legal) давала `Generic 0.000`, а одно поле
`contract.number`, из этой же фразы и извлечённое, — уверенный `Legal 0.667`.
Поле не может быть сильнее фразы, из которой получено.

Код при этом противоречил собственному комментарию:
«Require at least two independent weak signals (score >= 4)» — но одно поле
давало ровно 4.

Исправлено насыщением: первое пространство имён домена даёт 3 (ниже сильнейшей
фразы), каждое дополнительное пространство имён того же домена — ещё 1,
повторные поля внутри пространства — ноль. Это возвращает коду его
объявленное намерение.

Последствие, измеренное на сценариях: вход «договор № 1 от 01.01.2026»
(четыре слова) больше не запускает автоматическую генерацию комплекта.
Все шесть поддерживаемых профессий с полным текстом маршрутизируются
по-прежнему.

### Ранжирование выбрасывалось при сборке комплекта

`normalize` в `bundle_decision.rs` собирала идентификаторы в `BTreeSet`,
то есть сортировала по алфавиту. Маршрутизатор ранжирует кандидатов по
оценке, а сборка это ранжирование теряла: для источника «Приказ о приёме»
специалист видел `["hr.employment_contract", "hr.employment_order"]` —
трудовой договор первым, потому что он раньше по алфавиту.

Порядок маршрутизатора теперь сохраняется, дедупликация — без сортировки.

### Аллокации в горячем пути (дефект, внесённый ранее в 18.4.0)

Найден clippy. Первая реализация реестра рисков вызывала `serde_json`
и собирала `Vec<String>` на каждое обращение — девять аллокаций на одно
поле, при том что `field_risk` вызывается для каждого поля каждого
документа. Реализация 18.3.2 была без аллокаций вовсе.

Реестр теперь разбирается один раз в `OnceLock` в типизированную структуру
с `BTreeSet`. Заодно изменено направление деградации: битый JSON давал
«всё Low», то есть открывал автоматизацию для ИНН и диагнозов; теперь
`Critical` (fail-closed).

## Открытый дефект целостности данных

**Документ-спутник выпускается под номером документа-источника.**

Воспроизведение: источник «ДОГОВОР ПОСТАВКИ № 77 от 03.03.2026»
даёт комплект из договора и акта приёма-передачи. Результат рендеринга:

```
[legal.contract]        ДОГОВОР № 77 от 03.03.2026
[legal.acceptance_act]  АКТ № 77 от 03.03.2026 к договору
```

У акта приёма-передачи обязан быть свой номер, а его дата обычно позже
даты договора. Причина: `document.number` и `document.date` — общие поля,
заполняемые из источника, и любой шаблон-спутник, использующий
`{{document.number}}`, получает номер источника.

Не исправлено намеренно. Корректное решение требует определить, что
пространство `document.*` означает для документов-спутников: идентичность
источника, собственный счётчик или обязательный вопрос специалисту.
Это продуктовое решение, а не техническое.

## Что осталось нерешённым

**Заявленная цель по-прежнему недостижима, и одним изменением кода
её не достичь.**

| Что | Состояние |
|---|---|
| E1 для дат | `document.date` = 0.95 при High 0.98. Контрольной суммы у даты нет. Остаётся заблокировано |
| E2 — автопечать «из коробки» | Требует подписанного артефакта калибровки, для которого нужен корпус. Корпус набирается только эксплуатацией. Механизм для этого уже есть — `threshold_calibration.rs` + `corpus_recorder.rs`; он не сломан, он просто не наполнен |
| E7 — 87% тестов grep по исходникам | Заменены 2. Остальные ~163 на месте |
| E11 — 17 захардкоженных ролей | «Любая сфера» не решена |

Правильный следующий шаг — не архитектура, а **корпус**: включить
`corpus_recording_enabled`, накопить решения специалистов, прогнать
существующий `scripts/calibrate_thresholds.py`, получить подписанный
артефакт. Инфраструктура для этого написана и подписана. Ей не хватает
только данных.
