# Roadmap: как собрать «магию» понимания документа

**Проект:** Dokkomplekt Universal 18.2.2
**Цель:** специалист кладёт первичный документ → система сама делает весь комплект → предлагает печать. Абсолютное уничтожение рутины.
**Принцип, который нельзя нарушать:** модель *предлагает*, Rust *проверяет*, в документ попадает только *доказанное*. Автономию наращиваем домен за доменом, всё неуверенное уходит в быстрый review-фолбэк.

---

## 0. Карта: «магия» — это 4 слоя, а не одно чудо

| Слой | Что делает | Сложность | Готовность у вас |
|------|-----------|-----------|------------------|
| 1. Чтение байтов | скан/PDF/фото → текст+структура | низкая (индустрия решила) | обвязка есть, бинарников нет |
| 2. Понимание текста | текст → факты с верным смыслом | средняя | транспорт+grounding+consensus есть (~70%) |
| 3. Выбор комплекта | источник → *какой набор* документов | **высокая (доменная)** | нет, кроме каркасов |
| 4. Гарантия правильности | утверждённые формы + порог уверенности | юридическая, не ML | валидаторы есть, порога нет |

**Единственное настоящее узкое место — не модель и не OCR. Это размеченный доменный корпус пар «источник → правильный комплект».** Без него нельзя ни измерить, ни откалибровать, ни доказать «правильно». Всё ниже подчинено тому, чтобы этот корпус собрать дёшево и рано.

---

## Фаза 0 — Фундамент (разблокирует всё остальное)

**Задача:** дать системе физически читать и думать. Без этого «любой документ» — пустое слово.

- **0.1 OCR/конвертация-сайдкары.** Довести до реальной поставки Tesseract + Poppler + LibreOffice через уже готовую hash-verified staging. Хуки существуют: `scripts/prepare_sidecars.py`, `scripts/assert_offline_runtime_ready.py`, `scripts/verify_offline_runtime_bundle.py`. Тут не нужен новый код — нужны проверенные бинарники и прогон гейта.
- **0.2 Локальная модель.** Довести llama.cpp/GGUF staging до сборки офлайн-installer (сценарий уже блокируется без него). Транспорт готов: `src-tauri/src/semantic_model.rs` (`complete_many`, `consensus_sampling_profile`, loopback-only).
- **0.3 Раскладочный разбор.** Убедиться, что нормализация (`universal_intake::normalize_path`) сохраняет таблицы и формы из OCR-слоя, а не только плоский текст — иначе слой 2 получит кашу.

**Критерий выхода:** скан-PDF на входе → корректный текст+таблицы в case. Без ручной подготовки.
**Оценка:** недели, в основном упаковка и проверка. Исследований нет.

---

## Фаза 1 — Schema-constrained grounded extraction (усилить слой 2)

**Задача:** превратить «модель что-то извлекла» в «модель заполнила именно наши именованные слоты, с доказательством».

- **1.1 Целевая схема вместо свободного извлечения.** В `build_extraction_prompt` подавать модели не «извлеки факты», а точный список слотов домена (`contract.number`, `subject.name`, `org.inn`…) с типами. Модель обязана заполнять слоты, а не изобретать поля. Это отличает `contract.number` от `invoice.number` — сейчас главный источник путаницы.
- **1.2 Grounding оставить как есть — это уже сделано правильно.** Значение принимается, только если есть дословная цитата и Rust локализовал значение внутри неё. Не ослаблять.
- **1.3 Consensus → сигнал уверенности.** Расширить `apply_model_consensus_with_source`: число совпавших независимых проходов и разброс сэмплинга превратить в числовой `confidence ∈ [0,1]` на каждое поле, а не только бинарный «два совпали».
- **1.4 Всё логировать в case (зашифрованно):** поле, значение, цитата, число проходов, confidence, источник (deterministic/model/user). Это сырьё для Фазы 4 и для корпуса.

**Критерий выхода:** каждое поле в case имеет источник, цитату и калиброванный (пока грубо) confidence.
**Оценка:** 2–4 недели поверх существующего кода.

## Фаза 2 — Первый доменный корпус малой кровью (снять узкое место)

**Это самая важная фаза. Всё остальное без неё — угадайка.**

**Задача:** получить размеченные пары «источник → правильный комплект» *не* нанимая разметчиков, а из реальной работы одного пилотного специалиста.

- **2.1 Один домен, один пилот.** Выбрать самый узкий поток (например, кадры: приём на работу → контракт+приказ+согласие+лист ознакомления). Не «все сферы» — один поток.
- **2.2 Shadow-mode как сборщик корпуса.** У вас уже есть shadow-mode (`shadow_mode` в `automation_runtime.rs`): модель работает на клоне case, ничего не пишет, только фиксирует совпадения/отклонения. Использовать его как пассивный логгер: специалист работает как обычно (детерминированный путь + ручные правки), а система записывает `(вход, финальный принятый комплект, что модель предложила, что специалист исправил)`.
- **2.3 Каждое исправление специалиста = золотая метка.** Когда человек правит поле или добавляет документ в комплект — это и есть ground truth. Бесплатно, из реальной работы. 50–100 реальных дел одного специалиста дают первый измеримый корпус.
- **2.4 Формат хранить в вашей же content-pack схеме.** `content-packs/manifest.schema.json` уже описывает слоты и workflow. Корпус — это накопленные подтверждённые прогоны против пака.

**Критерий выхода:** ≥50 размеченных дел одного домена, на которых можно *посчитать* точность извлечения и полноту комплекта.
**Оценка:** 2–6 недель календарно (ограничено темпом пилота, не разработкой). Разработки мало — в основном логгер и экспорт.

## Фаза 3 — Выбор комплекта (слой 3, доменное ядро)

**Задача:** «из этого источника нужны документы X+Y+Z». Два пути, ведём оба параллельно.

- **3.1 Курируемые kit-правила (детерминированный костяк).** Тип источника → обязательный набор выходов, по юрисдикции. Экспертная работа, срезать нельзя. Ложится в существующие доменные профили (`crates/dokkomplekt-core/src/domains/*.rs`) и content-packs. Начать с одного домена из Фазы 2.
- **3.2 Обучение на истории (масштабируемая надстройка).** На корпусе Фазы 2 кластеризовать «когда приходил документ типа A, специалист делал набор B». Предлагать набор, но **никогда не выбирать молча** — показывать «предлагаю комплект: …, подтвердите». Расширить существующий механизм learned scanner rules (`apply_learned_scanner_rules`) с полей на уровень комплектов.
- **3.3 Промоушен правил по метрикам.** Правило переходит из «предлагать» в «применять автоматически» только после N подтверждений подряд с нулём исправлений на корпусе. Метрика, а не интуиция.

**Критерий выхода:** для пилотного домена система сама предлагает правильный состав комплекта в ≥90% дел (замерено на корпусе).
**Оценка:** 4–8 недель на первый домен; каждый следующий домен дешевле за счёт переиспользуемого механизма.

---

## Фаза 4 — Порог уверенности и безопасный фолбэк (гарантия «правильно»)

**Задача:** честно ответить на «абсолютно правильно» — не 100% автономии, а 100% корректности за счёт того, что недоказанное никогда не печатается молча.

- **4.1 Три корзины по confidence (из Фазы 1):**
  - высокая → авто-заполнить, авто-собрать, предложить печать;
  - средняя → собрать, но показать «проверьте эти N полей» перед печатью;
  - низкая → в review-очередь, не печатать.
- **4.2 Порог калибровать, а не назначать.** На корпусе Фазы 2 построить кривую «confidence vs фактическая доля ошибок» и выставить порог так, чтобы доля ошибок в авто-корзине была ниже согласованного предела (например < 0.5%). Это и есть измеримое «правильно».
- **4.3 Diff перед печатью.** Показывать «что подставилось и откуда» (у вас уже есть `ПРОВЕРИТЬ_КОМПЛЕКТ.txt` — вынести в UI как обязательный шаг для средней корзины).
- **4.4 Формы — только утверждённые.** Пока пак `draft_only`, авто-корзина запрещена для него на уровне контракта (у вас уже есть запрет статуса `pilot/approved` без проверенных DOCX — расширить на порог печати).

**Критерий выхода:** доля ошибок в авто-печатаемой корзине измерена и под целевым порогом; всё сомнительное уходит в 10-секундное ревью.
**Оценка:** 2–4 недели поверх Фаз 1–2.

---

## Как измерять «правильно» (иначе весь roadmap — вера)

Три числа на каждый домен, считаются на корпусе Фазы 2:

1. **Field accuracy** — доля полей, где принятое значение = ground truth.
2. **Kit completeness** — доля дел, где предложенный состав комплекта = фактический.
3. **Error rate в авто-корзине** — доля ошибок среди того, что система напечатала *без* ревью. Это главный KPI. Цель: заведомо ниже ручного уровня ошибок специалиста.

Автономию домена повышаем, только когда все три под порогом. Не раньше.

## Порядок и зависимости

```
Фаза 0 (runtime+OCR) ──┬─> Фаза 1 (grounded extraction)
                       │        │
                       │        v
                       └─> Фаза 2 (корпус, shadow-mode) ──┬─> Фаза 3 (выбор комплекта)
                                                          └─> Фаза 4 (порог + фолбэк)
```

- Фаза 0 разблокирует всё.
- Фазы 1 и 2 можно вести параллельно.
- Фазы 3 и 4 обе питаются корпусом Фазы 2 — до него не начинать всерьёз.
- Первый полный проход = один домен end-to-end. Второй домен переиспользует Фазы 0/1/4 почти целиком.

---

## Чего НЕ делать (границы, которые защищают вас)

- **Не обещать «литерально любой документ, ноль настройки, ноль ошибок».** Этого нет ни у кого. Обещать: домен за доменом — высокая автономия, везде остальное — быстрый безопасный ревью.
- **Не давать модели решать юридическую правильность без верификации.** Как только LLM пишет в документ без grounding+валидатора — «магия» становится источником ответственности.
- **Не масштабировать на все сферы сразу.** «Универсально» достигается сложением доменов, а не одним универсальным парсером.
- **Не ослаблять grounding ради покрытия.** Лучше корзина «в ревью», чем тихая ошибка в напечатанном документе.
- **Не считать текстовый marker доказательством.** Держать Ed25519-аттестацию и измеримые метрики как единственное «доказано».

---

## Итог одной фразой

«Магия» = поставленный runtime (Фаза 0) + grounded schema-extraction (Фаза 1) + **дешёвый корпус из реальной работы одного пилота** (Фаза 2, узкое место) + доменные kit-правила (Фаза 3) + калиброванный порог с ревью-фолбэком (Фаза 4). Архитектура проекта уже построена ровно под этот инкрементальный путь — задача не изобрести чудо, а пройти пять фаз, не сломав принцип «печатается только доказанное».
