# Dokkomplekt Universal 18.2.2 — Adversarial Hardening Report

## Почему появилась версия 18.2.2

Версия 18.2.2 создана после намеренно разрушительного аудита 18.2.1. Целью было не добавить ещё один набор функций, а устранить классы дефектов, которые могли привести к молчаливо неверному документу, вечной блокировке watcher, повторной обработке на нескольких машинах, недостоверному resume или подделываемому release evidence.

## Исправленные классы дефектов

### 1. LLM self-consistency больше не повторяет один детерминированный ответ

Высокорисковые значения проверяются проходами с различными seed, temperature и формулировкой проверочного запроса. Совпадение одинаковых ответов одной deterministic-конфигурации больше не считается независимым консенсусом.

Это не превращает LLM в источник истины. Модель по-прежнему только предлагает значения, а high-risk автоматизация требует grounding и детерминированных валидаторов.

### 2. Grounding ФИО и адресов усилен

- для ФИО требуется локализация всех значимых токенов, поэтому неверное отчество больше не проходит по совпадению имени и фамилии;
- для адреса должны совпадать все числовые компоненты и достаточная доля лексических токенов;
- нормализуются пробелы, переносы, NBSP, кавычки и тире;
- добавлены отрицательные регрессии для другого отчества, дома и квартиры.

### 3. Watcher различает постоянные и временные ошибки

Повреждённый источник остаётся заблокированным до изменения содержимого. Ошибки отсутствующего компонента, временной инфраструктуры, лицензии или сети получают ограниченный retry с категорией и сроком следующей попытки.

Диагностика больше не сводит все форматы и причины к совету «пересохраните Word».

### 4. Watcher не перечитывает полную папку каждые две секунды

Native filesystem events добавляют изменившиеся пути в очередь. Полный fallback scan выполняется значительно реже и предназначен для SMB/NFS, где события могут теряться. Полный SHA-256 вычисляется только для фактически ожидающих путей.

### 5. Дедупликация связана с планом обработки, а не только с исходником

Processing fingerprint включает:

- SHA-256 источника;
- версию приложения;
- набор и содержимое шаблонов;
- workflow-настройки;
- настройки модели и hashes runtime/model;
- производственный календарь;
- параметры, влияющие на генерацию.

Изменение шаблона, workflow или справочника создаёт новый валидный прогон даже при неизменном исходнике.

### 6. Resume проверяет целостность готового документа

Для каждого checkpoint сохраняются SHA-256 и размер результата. Файл переиспользуется только при совпадении:

- dependency fingerprint;
- SHA-256 готового документа;
- размера;
- ожидаемого пути и статуса.

Изменённый, повреждённый или подменённый checkpoint пересоздаётся.

### 7. Очередь получила heartbeat и retention

PostgreSQL claim продлевается фоновым heartbeat. Завершённые и retryable записи очищаются по retention. Файловые completion receipts также удаляются гигиеной рабочей папки.

PostgreSQL transport всё ещё использует `NoTls`; он разрешён только в доверенной локальной/VPN-сети и не объявляется готовым публичным queue service.

### 8. Скачанный semantic runtime реально запускается

Добавлен supervisor для доверенно установленного `llama-server` и GGUF:

- выбор loopback-порта;
- запуск дочернего процесса;
- ожидание готовности;
- проверка раннего завершения;
- остановка процесса при замене конфигурации или выходе приложения.

Статус `downloaded` больше не означает установленный, но неиспользуемый runtime.

### 9. Component installation восстанавливается после аварии

При старте проверяются `.installing`, `.previous` и частичные загрузки. Полностью проверенная предыдущая версия восстанавливается, а устаревшие транзакционные остатки удаляются. Восстановление повторно сверяет manifest и hashes каждого файла.

### 10. Runtime state и audit chain усилены

JSON runtime-state и content-block данные сохраняются через существующий sensitive-state codec. Новые audit-chain записи используют keyed HMAC, а не только публичный SHA-256.

Ограничение остаётся: HMAC-цепочка не имеет внешнего trusted timestamp/anchor и не является юридически значимым неизменяемым журналом.

### 11. Cargo gate стал подписанной аттестацией

Обычный текстовый `CARGO_GATE_PASSED.ok` больше не является release evidence. После настоящего Rust gate создаются Ed25519-подписанные:

- `.cargo-gate/CARGO_GATE_ATTESTATION.json`;
- `.cargo-gate/CARGO_GATE_ATTESTATION.sig`.

Аттестация связана с source fingerprint, `Cargo.lock`, commit SHA, CI run identity, Rust/Cargo versions и точным набором выполненных checks. Подмена payload обнаруживается.

Gate не запускает `cargo fmt` в режиме исправления: релиз падает, если проверяемое дерево не отформатировано.

### 12. Windows evidence больше не имитирует reboot и печать

- установленный EXE определяется по точным product metadata, а не как первый найденный `.exe`;
- при release-проверке требуется Authenticode установленного приложения;
- print test требует событие Windows PrintService ID 307;
- повторный запуск процесса не называется reboot;
- отдельный verifier требует evidence двух разных boot IDs и завершённого watcher-case после перезагрузки.

Эти проверки добавлены в CI, но не выполнены в текущем Linux-контейнере.

### 13. Расширен реальный DOCX-корпус

Добавлено семь детерминированных DOCX fixtures с:

- merged tables;
- секциями и landscape;
- длинной пагинацией;
- изображениями и колонтитулами;
- формулами и условиями;
- content controls, fields и tracked changes;
- comments и relationships.

Visual verifier рендерит их через LibreOffice, проверяет XML/relationships, blank pages, размеры и perceptual hash каждой страницы.

## Что сознательно не выдано за исправленное

- Rust backend не скомпилирован в текущем окружении: отсутствуют `cargo` и `rustc`;
- Windows hardware E2E и реальная перезагрузка не выполнены здесь;
- реальные vendor sidecars и GGUF не входят в source archive;
- actions всё ещё используют version tags, а не все pinned commit SHA;
- `include!`-декомпозиция shell снижает размер файлов, но не создаёт строгие module API;
- PostgreSQL queue не использует TLS/mTLS;
- audit chain не имеет внешнего anchor;
- КЭП/Госключ и сертифицированный PDF/A не реализованы;
- professional Tier-1 content packs требуют профильного утверждения.

## Итог

18.2.2 закрывает наиболее опасные дефекты 18.2.1 на уровне исходников, контрактов и доступных runtime-проверок. Она остаётся source candidate, пока подписанная Cargo-аттестация и Windows hardware evidence не созданы на соответствующих runners.
